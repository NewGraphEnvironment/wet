## Findings

- **[severity: bug]** tests/testthat/test-air_publish_lib.R:57, :70, :73. The test calls `arrow::read_parquet()`, but `arrow` is not listed in DESCRIPTION (Imports or Suggests). I ran `tools:::.check_packages_used_in_tests(".", testdir = "tests/testthat")` on the branch and it prints `'::' or ':::' import not declared from: 'arrow'`. `R CMD check` raises that as a WARNING ("checking for unstated dependencies in 'tests'") even though `air_lib()` skips at run time. The scan is static. The repo's R-CMD-check workflow (flows `r-cmd-check.yaml@v1`) fails on warnings, so the PR goes red. `scripts/air_publish_lib.R` also needs arrow, but scripts/ is build-ignored, so only the test file trips the check. Fix: add `arrow` to Suggests.
  - **Rule:** code-check-r.md "A `pkg::` call in a test passes `devtools::test()` and fails `R CMD check` if `pkg` is undeclared"

- **[severity: fragile]** scripts/air_station_check.R:99–100 and :115. The match keys are built with `paste()` from mixed types. `at_seg$id` and `xs$seg` are doubles (from `wet_station_snap()`'s `linear_feature_id::double precision`), while `a$id` is integer (`wet_air_daily()` returns `as.integer(segments)`). R pastes a whole double with three or fewer significant digits in scientific form: `paste(701000000)` gives `"7.01e+08"` and `paste(17000000)` gives `"1.7e+07"`, but the integer gives `"701000000"` (checked in R). For such a segment, every row of `at_seg` and `xs` misses its partner in `a`. It is counted as differing, and the station check reports FAIL on a correct tree. This is rare (ids with trailing zeros) and fails toward fail, but the false failure would be hard to explain from the report. Fix: build the keys from `as.integer(id)` on both sides, or match on integer columns rather than pasted strings.
  - **Rule:** none

- **[severity: fragile]** scripts/air_publish.R:255–256 and :265. The checks read the frame, not the written tree. `air_check_complete(y, …)`, `air_check_values(y, …)` and `air_check_cells(lookup, …)` all run on the in-memory frames passed to `air_part_write()`. None of them reads a written part back, yet the report says "Checks (none passes through the code that made the tree)". The only reads of the parts are `wet_manifest_write()` counting rows from the parquet metadata and `wet_catalog_verify()` comparing md5s against that same manifest, which is self-consistency. Nothing compares the manifest's `rows` with `nrow(lookup)` or with the sum of the year frames. So a part that lost or gained rows on the way to disk would pass every BUILD check. Today `air_part_write()` writes every row and casts safely, so this is a latent hole, not a live bug. The discharge publish reads every part back (#64). Cheap fix: assert `sum(rows of segment_cell) == nrow(lookup)` and `sum(rows of cell_daily) == sum of nrow(y)`, or run the completeness and values checks on `arrow::read_parquet()` of each written year part.
  - **Rule:** code-check.md "A guard that fails toward pass" (What the guard reads: "whether it reads the artifact you write or the frame you write it from: one direction refuses a correct release, the other passes a lost row")
