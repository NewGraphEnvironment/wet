# Code-check round 1 (#25, branch vs main incl. staged)

## Findings

- **[severity: bug]** R/wet_station_daily.R:66 (`pv <- wet_daily_after(pv, hy)`), with the helper at :94-99 — the per-station cutoff comes from HYDAT rows that were **already filtered to `from`/`to`**, not from HYDAT's real last day. When `to` falls inside HYDAT's record and the window ends in a HYDAT hole, or when the whole window sits in a HYDAT hole, `last` is too early. Provisional days then fill a hole inside the approved record. That breaks the documented contract ("provisional days are used only after HYDAT's last day"; the code comment says they "never fill a hole inside HYDAT's approved record"), and the same day comes back from a different source depending on the query window. Reproduced in a temp copy with the test fixture and the same provisional mock as the test "provisional flows continue HYDAT and never fill a hole inside it":
  - `wet_station_daily("08AA001", h, to = "1985-01-10", sources = c("hydat","provisional"))`: 1984-07-25 is absent (correct).
  - `wet_station_daily("08AA001", h, from = "1984-07-01", to = "1984-07-31", ...)`: 1984-07-25 is returned as `provisional`, q = 100, inside HYDAT's July 1984 hole, with a seam-gap warning.

  It matters in practice because the provisional archive (since 2024-10) overlaps HYDAT's tail (to 2025-03 for the study stations). Any call with `to` or `from` in that overlap is exposed, including the kind of `from = 2025-11-15` spot check findings.md records. The real-time cutoff (`have`, :71-78) has the same flaw one level down: `have` is window-filtered, so real-time can fill a provisional hole just before `to`. The cutoff should come from each source's unfiltered last date per station (for example `SELECT STATION_NUMBER, MAX(YEAR*100+MONTH)` plus the last non-NULL day, or a read of HYDAT with no date bound for the cutoff only), not from the rows kept for output.

- **[severity: fragile]** tests/testthat/test-wet_station_daily.R:205-210 (live test) — the fallback cannot pass. `test_path("..", "..", "data", "hydat", "20260717", ...)` points outside `tests/testthat`, so under `devtools::check()` / `R CMD check` (from `<tmp>/wet.Rcheck/tests/testthat`) or on any clone without that download, it falls back to `local_hydat_real()`, which is tidyhydat's default HYDAT. On this machine that file is version 2025-10-14, and its last 08EE013 month is 202312 (measured). With `from = "2024-01-01"` there are no `hydat` rows, so `expect_setequal(unique(d$source), c("hydat","provisional","realtime"))` fails. (The seam-gap warning for 2024-01 to 2024-10 also fires.) The test is `skip_on_ci()`, so CI stays green, but a local `devtools::check()` online goes red. The fallback runs in exactly the case where it cannot pass.

- **[severity: fragile]** scripts/station_departure.R:125 — `stats::aggregate(year ~ variable + period, s[s$year %in% baseline, ], length)` errors with "no rows to aggregate" when a station has no window-year inside 1981-2010. This is the checklist's aggregate-on-empty-subset trap. The script is documented as `Rscript scripts/station_departure.R [STATION ...]` "for real-time stations", and many of those start after 2010. Such a station passes the MAD step, because `mad_all` falls back to its whole record, then aborts here. Nothing is written, because `writeLines(out, report)` runs only after the loop over all stations. The same crash follows one step later when every window is thin (`keep` empty, so `s` has zero rows, and it goes into `cd::cd_baseline()`/`cd_anomaly()`/`merge()`/`cd_trend()`). Guard on `nrow()` and report the station as having no baseline, rather than stopping the run.
