# Task: Build one watershed group's segment product from a published fit? (#157)

**If we do it:** one basin's segment discharge can be rebuilt from a changed input or parameter in minutes instead of a province run, and an app could compute a scenario for one site (a different climate period, say). **If we never do:** every change waits for a province run, and anything outside the published product is out of reach.

## Question

Is a per-group build worth having, and what is its smallest shape? As it stands:

- `scripts/segment_output.R` needs the shipped province fit (`fits.rds`, not published), a clean tree and the complete province run.
- Accumulation runs per basin (`scripts/wb_province.R` samples per group and sums upstream per basin), so a group needs the groups upstream of it.
- `scripts/wb_inputs.R` fetches from figshare, TerraClimate, PCIC and Environment Canada.

## What exploration established (2026-11-04, m1 fwapg and m4's province run `92b893c4da`)

- **The fit is tiny and self-contained.** `fits.rds` is 43 KB and holds everything `wb_output.R` applies: `wb` (zone coefficients), `share` (donor fit: calibration gauges' scaled predictors and observed shares, `k = 5`), `keep_adjust`, `aet`, `code_md5`, `share_method`. Applying it is four package calls (`wet_wb_raw()`, `wet_wb_adjust()`, `wet_share_predict()`, `wet_mm_to_m3s()`; `scripts/wb_output.R:56-73`).
- **"The groups upstream of a group" is a code-prefix closure, not a lookup.** `wet_upstream_sums()` sums over `(wscode, localcode)` ranges, so for the group's rows it needs only the polygons whose `wscode` lies under the group's *root* codes (its distinct wscodes with no proper ancestor in the group). `FWA_Upstream(a, b)` requires `b`'s wscode to descend from `a`'s in both of its branches, so that set is closed, and the sums for the group's rows equal the basin run's to summation order (the segment tree's leaf positions differ, so last bits can move; expect ≤ 1e-12 relative). Confirmed by brute force: no FWA_Upstream pair from a BULK polygon leaves `400.431358`. Measured over all 246 groups (psql, 24 min): **53 groups need only themselves, 59 need 2–3 groups, 62 need 4–10, 72 need more than 10**; 146 closures are under 50k polygons, 48 over 200k. BULK: one root, BULK + MORR, 35,191 polygons; SALR: SALR + LSAL + MUSK, 12,481; LNRS: 19 groups, 116k. The 48 big ones hold a Fraser, Peace or Columbia mainstem polygon whose `localcode == wscode` (`100`), and for such a row `FWA_Upstream` is the whole subtree, so under fwapg's own semantics those groups need the whole basin (MORK, SETN, TWAC, UFRA: 70–82 groups, 645k polygons; LFRA 77). A position-aware refinement (keep only polygons at or above the group's lowest code) was tried and changes none of them, so the simple root-subtree rule stands. 54 groups span more than one top-level drainage code. So the build is worth having for the tributary and headwater groups (about half the province's groups, the kind the Chinook pilots sit in) and is a basin run for a mainstem group; Phase 1 writes that table as the tracked record.
- **The cost is seconds, on the machine with `layers.tif`.** m4's province run sampled BULK in 10 s and MORR in 8 s (`sample_times.txt`) and accumulated the whole province in 4.5 min. m4 holds `layers.tif` (552 MB), `in_bc.tif` and all 246 `sample/<WSG>.rds` (1.1 GB). m1 has none of them (reduced bundle), so the script is developed on m1 and run on m4 over ssh.
- **The published rows of a group** read in about a second from the parts (duckdb, httpfs, `watershed_group_code` filter; measured on BULK: 390,481 balance rows, 30,037 segments, 10,569 picked, matching the segment report). The live build b4bbc50 is this same fit, so parity against the published product is the right test. The publish drops watershed rows whose `q_m3s` is NA (`discharge_publish.R:334-336`) and keeps balance segment rows only where the watershed has a value, so the group build must drop the same rows before comparing.
- **Two code-hash constraints shape where code goes.** (1) `wb_province.R`'s key hashes the script and 13 `R/` files (`R/wet_ws_fetch.R`, `R/wet_upstream_sums.R`, `R/wet_upstream_means.R`, `R/wet_ws_sample.R`, …) and `wb_score_md5.R` hashes the fit's scoring files. Editing a scoring file stales the fit at once (`wb_output.R:36`, `segment_output.R:71`); editing a key file, a roxygen line included, gives the *next* province run a new key and a full resample. So every new function lands in a **new file** and those files are not touched. (2) The publish refuses a segment table whose `R/` or `scripts/` moved since its report (all but the publish's own files); 21 files have already moved since 28105a3, so the rerun is owed since #117 and this branch adds no new obligation.
- **What a published fit would not buy.** Without `layers.tif` (or the samples) no one outside m4 can run the sampling, and a climate scenario needs new input layers (`wb_inputs.R`'s chain), not only the fit. And the manifest lists `part-<code>.parquet` keys only (`wet_manifest_write()`, `wet_part_parse()`), so a published `fits.rds` means a manifest-format change, not one object. Cheap in bytes, not in code, and it needs a BUILD + PUBLISH on m4 (hours) under the publish's digest gate.

## Decided at the gate

Plan approved parked by the user, 2026-11-04 (the `PARKED: baseline only` header): the baseline is written and pushed; the run-to-PR mandate starts at the resume block in `progress.md`.

1. **Publish the fit in this branch, or file it as a follow-up?** Recommended and taken with the approval: **follow-up.** The script reads the shipped fit from the fit directory under the same guards as `segment_output.R` (`code_md5` = `score_code_md5`, `aet_winner.txt`), so the issue's steps 2–4 are answered without it; the follow-up issue names what a portable build actually needs (the manifest change for a non-parquet object, and the samples or `layers.tif`), filed only if Phase 1's table says the build is worth having. Alternative not taken: change the manifest format and publish code now, then a BUILD (~3.5 h) and a PUBLISH on m4.
2. **What the group build produces** (mechanism, stated for the record): the balance only, the group's watershed rows and `wet_balance` segment rows for 13 months, with `pick` recomputed by `wet_source_pick()` against the published routed annual flow and fwapg's own-line test. Routed PCIC and the daily shape are not rebuilt (neither comes from the balance's inputs).
3. **Scope out:** refitting (the issue says so), the daily product, any change to the province chain's files, a package-level sampler (the script carries its own copy of `sample_group()`; the extraction goes with the fold-in below).
