- **[severity: fragile]** scripts/wb_aet_compare.R:207-209 and 237-241. The report's prose can contradict its own table. The "## As shipped" table lists all ten variants, and it sits inside the Stage 1 section, directly above "(a)-(c) choose: <stage 1 winner>". fu15/fu20/fu35 are tagged "(transparency)" there, which tells a reader why stage 1 skips them. mod16 and cmod16 have no tag, yet stage 1 never considers them either (`decide(top, "cgiar", eligible)`). If a MOD16 variant does what #18 hopes, for example headwater 28 and within (a)-(c) of cgiar, the report shows that row with a lower headwater MAE than cfu and then, right under it, "(a)-(c) choose: cfu". The Stage 2 section further down gives the real answer, but the Stage 1 block reads as a rule that ignored its best row. A fix is to tag the eligible2 rows too, e.g. `ifelse(top$aet %in% eligible2, "(stage 2)", ...)`.

- **[severity: fragile]** scripts/wb_inputs.R:57, 125-131. The manifest row "MOD16A3GF v061 annual ET, 2001-2020 (%d granules)" hashes every `MOD16A3GF.*.hdf` in `data/mod16`, not the granules `wet_mod16_aet()` actually read. That function reads exactly tiles(grid) x years through `wet_mod16_local()`. Any other granule in the directory raises the count and changes the combined md5, while the grid, and its md5 in the next row, stay the same. That could be another year, one of the three CMR-only tiles, or a probe or `@examplesIf` download into the default `dir`. The manifest would then disagree with its own label. Today the directory holds exactly the 180 granules (9 tiles x 2001-2020, checked), so the tracked file is correct now. It is not guaranteed to stay correct. Filtering `f_m16_granules` by year 2001-2020 and by `wet:::wet_modis_tiles()` of the grid would tie the row to what was read.

## Checked and found correct

- **The round-1 fix is labelled correctly.** wb_province.R:137-141 computes `fr == 1` (mod16_whole), `fr == 0` (cfu_whole), `0 < fr < 1` (cfu_part) and `sum(1 - fr)`, all on the analysis mask (`fr` is masked by `bad`; `na.rm = TRUE`). The report line at wb_aet_compare.R:256-257 explains each label as what it counts. `%d` on a whole-number double is fine.
- **ns_inc report line.** The line says "inner gate per fold", which is what `nested_select(function(m) inc)` does: each fold's `keep` and `pv` come from its own training stations. The line makes no claim about which bar is stricter. The (d) line states the comparison against "cfu as shipped: headwater X". The Stage 2 rule sentence says "beating the as-shipped headwater MAE of cfu on this run". Both match `pass_d2 <- ns2$metrics[["hw"]] < inc_row$hw` and the approved rule. The claim "(d) is the stricter of the two bars" appears only in a code comment (line 170), where it holds for the dry run, not in general.
- **Stage 1 path.** `ns1` subsets `fold_m` to `cands` in #15's order, so `decide()` and `which.min` tie-breaks are unchanged. `m$keep`/`m$pv` for the chosen variant are the same values the old per-fold `m` held. The reproduction check covers the 7 top-table columns for all 8 #15 variants, (a)-(c), the nested metrics and the fold counts (`as.vector(table)` is integer, so `identical(..., c(0L,0L,0L,6L,87L))` is sound). It runs after `aet_winner.txt` is unlinked, so it fails safe.
- **Stage 2 rule vs task_plan.** `decide(top, inc, eligible2)` restricts candidates to mod16/cmod16. The in-fold selection is among {inc, mod16, cmod16}. The winner needs both the top-level rule and (d). Ties go to the lowest hw. `ns12` runs stage 1 then stage 2 per fold with that fold's own stage-1 winner, as the plan's transparency row describes.
- **Transparency rows.** `hi16` includes the headwater condition, and the printed n uses the same `hi16 & obs >= 10` mask as the mean. `vapply` over a character vector names the results. The MOD16-share quantiles are over all `nrow(cal)` stations, as labelled. `frac_mod16` reaches `cal` through sampling and `wet_upstream_means` like any other layer, so it is a basin-area share.
- **Variants line and province blend.** "mod16 (... gaps filled with cfu by area)" and "cmod16 (max of CGIAR and mod16)" match wb_province.R:133-134, where cmod16 is the max of cgiar and the filled layer. `m16x` is re-masked, and the unmoved-mask assertion covers the three new layers.
- **wb_validate.R / wb_output.R.** Both resolve the variant through `wet_wb_aet_cols()`, which now includes mod16/cmod16, and `layers.tif` carries `aet_mod16`/`aet_cmod16`, so shipping either works.
- **Manifest md5 ordering.** The granule names are fixed-width ASCII, so `sort()` gives the same order in any locale.
