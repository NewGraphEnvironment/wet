## Findings

- **[severity: fragile]** R/wet_bcwatertool.R:217-220: `wet_bcwatertool_credit()` reads `meta[["Data Licence Information"]]`, but `meta` is a named **character** vector (from `stats::setNames()` in `wet_bcwatertool_read()`), so when the key is missing it raises "subscript out of bounds" and never returns `NULL`. The `is.null(x)` branch can never run and the function never returns `NA`. Reproduced: a Tool CSV with no licence line, `wet_bcwatertool_read()` and then `wet_bcwatertool_credit()` gives `Error: subscript out of bounds`. Why it matters: data-raw/station_sources_bcwatertool.R:251 calls it for every listing, and its own refusal at :258 ("a Water Tool listing states no licence line: <numbers>") can never be reached. A new pin with one listing lacking the line would stop inside `vapply()` with a message that names neither the file nor the listing. The pinned 53 all carry the line, so today's registry is unaffected. Fix: `x <- meta[names(meta) == "Data Licence Information"]; if (!length(x) || is.na(x[[1]])) return(NA_character_)` (or `unname(meta["Data Licence Information"])` with an NA test).
  - **Rule:** code-check-r.md "`[[` on a named ATOMIC vector with an absent key is an error, not `NULL`"

- **[severity: fragile]** R/wet_station_daily.R:171-186 (with data-raw/station_sources_bcwatertool.R:224-229): round 1 moved the chain's cut from the provincial snapshot being read (`prov$first` of `snapshot`) into the Tool registry's `continues_before`. That value is measured on one provincial snapshot, `wet_bcenv_snapshot` at pin time (20261028), and the registry does not record which one. `wet_bcwatertool_station_days(stations, snapshot)` still takes the caller's provincial `snapshot`, and uses it to choose which continuations apply (`prov`) and for the conflict check, but the cut does not depend on it. Once a second provincial snapshot is pinned, a call with the other snapshot applies a cut measured on a different set of files. If that snapshot's first usable hour is earlier (the province rewrites its files in place), Tool days and provincial days overlap under one number, and `wet_station_daily()` has no guard against duplicate station-dates. If it is later, Tool days are wrongly cut. The harvest's `treg_cut` check catches this only for the snapshot the harvest runs on. This cannot happen today: only 20261028 is pinned, and any other snapshot is refused at its manifest. It becomes reachable at the next provincial pin. Fix: store the provincial snapshot beside `continues_before` in the registry (or key the column by it), and have `wet_bcwatertool_station_days()` refuse, or fall back to that snapshot's first usable day, when `snapshot` differs.
  - **Rule:** code-check.md "Written data outlives the fix"
