## Findings

- **[severity: fragile]** tests/testthat/test-wet_bcenv_daily.R:40 (fixture tests/testthat/helper-bcenv.R:43). The test named "the Peace keeps UTC-7" cannot fail when the UTC-7 branch is removed. I changed R/wet_bcenv_daily.R:122 to `THEN 8 ELSE 8` in the worktree and all 14 tests in the file passed (failed 0, error FALSE). The reason: 07ZZ0001's only day is 24 hours of one constant value with no neighbouring days. Moving the day boundary by an hour leaves 23 hours on 2020-06-02 (still at least 20) with the same mean, plus a 1-hour fragment on 06-01 that is dropped. So the decided rule (UTC-7 for drainage areas 07 and 10) is untested: a regression in that CASE, or in the `regexp_replace` on ids with leading letters, would ship silently and move the Peace and Liard stations' days by an hour. The Pacific side is covered: an offset of 7 there would pull a value-2 hour into 06-03 and change its mean.
  - **Rule:** code-check.md "A fixture that cannot reach the failure mode" ; code-check.md "Restore the bug and prove the guard fires"

- **[severity: fragile]** R/wet_bcenv_daily.R:87-90 with data-raw/station_sources_snapshot.R:59 and :117. The stored days are keyed only on the snapshot date and `wet_bcenv_reader`, never on the snapshot's contents. `wet_bcenv_days()` returns an existing `days_v1.parquet` without checking it against the manifest, and step 2 of the data-raw script rewrites `bcenv_<snapshot>.csv` in place for any snapshot other than 20261028, with nothing comparing it to an earlier manifest. Suppose a new snapshot is re-run after fixing its raw directory, for example after a first download that missed an archive file. Step 3 replaces the cached CSVs with the corrected ones, but step 5 (`wet_bcenv_daily(NULL, snapshot)`) and every later `wet_station_daily()` on that machine read days built from the old files. The registry's `first`/`last` are then written from those stale days. A machine with an empty cache builds from the new files, so two machines silently disagree under one pinned snapshot. The same happens wherever a manifest changes under an existing date. A fix: key the parquet on a digest of the manifest (or store the manifest's md5 beside it and rebuild on a mismatch).
  - **Rule:** code-check.md "Written data outlives the fix"

- **[severity: fragile]** inst/extdata/station_sources/bcenv_20261028_hydat.csv (`first`, `last`), written at data-raw/station_sources_snapshot.R:117-131, against R/wet_bcenv_daily.R:8-10 and R/wet_station_list.R:24. The header of wet_bcenv_daily.R says the bound, the hours rule and the status rule "are applied when the days are read, not stored, so changing one needs no rebuild". `wet_station_list()` documents `first`/`last` as "the first and last days wet_station_daily() returns". But the shipped registry bakes those rules into `first`/`last` (the bound, `min_hours = 20` and the negative-day drop). scripts/station_sources_bound.R tells the operator to set `wet_bcenv_bound` to the report's line, and nothing then rebuilds or checks the registry. Only the live test checks it, for one station (08EE0001). So a changed bound leaves `wet_station_list()` disagreeing with `wet_station_daily()` without any error. Today they agree: across the 211 stations I found 0 mismatches between the registry and `wet_bcenv_daily(NULL)`'s per-station ranges, and `wet_station_daily(<all 211>, sources = "bcenv")` returned the same 214,960 days with identical flows. So this is a contract with no guard, not a present defect.
  - **Rule:** code-check.md "One fact derived twice"

- **[severity: fragile]** data-raw/station_sources_snapshot.R step 4 (the `head$Metadata$md5` check). The backup check compares the object's `md5` metadata with `man$md5[i]`, but that metadata is the value the script itself passed with `--metadata md5=...` on the line above. So it can only ever agree, and only `ContentLength` says anything about the bytes stored. The header calls this backup "the only other copy of what was read". The aws CLI's own per-part MD5 check on upload reduces the risk, but the script's md5 check verifies nothing. The way to verify is the object's ETag against the file, trying the multipart part sizes for files of 57-150 MB.
  - **Rule:** code-check.md "Verification that reads its own output" ; code-check-shell.md "An S3 multipart ETag depends on the uploader's part size, so try every size that gives its part count"

- **[severity: fragile]** R/wet_bcenv_daily.R:142 and :196 (`wet_bcenv_lines`). The expected row count is the number of newline bytes minus the header. A correct file whose last data row has no trailing newline counts one line short, so it is refused as "a provincial file read a different number of rows than it has lines". That error message points at the parser, not the count. The pinned snapshot's files all end in a newline, so today's reads pass. A future snapshot, which the docs say needs no code change, would hit this on a correct file. One fix: count a final unterminated line.
  - **Rule:** code-check.md "One fact derived twice"
