## Findings

- **[severity: fragile]** data-raw/short_record_vignette_data.R:101 (`read_series()`) and :225 (`values$site`). The check that a series file is current tests only `x$site$site_id`, alongside the script's own md5. Before #146, the box and every gauge id were literals inside `scripts/departure_pilot.R`, so `code_md5` covered them. Now they live in `scripts/departure_sites.csv`, and `site_get()` lives in `scripts/departure_site_lib.R`. Neither is hashed. Suppose Maxan's row is edited and committed, for example its box, and `departure_site.R` is not rerun. The script then bundles the stale series with no complaint. The parity gate would catch the edit, but it runs only inside `departure_site.R`. `vd_commit()` then stamps the bundle with a commit whose CSV did not produce those series. That breaks the header's claim that "the commit the bundle names rebuilds it". The same stale run also feeds `values$site`, which is taken from today's CSV rather than from the run's own `x$site`. So `blue_line_key` and `name`, which the map script and the article key on, can disagree with the series beside them. `snow_gauges` and `target_station` are held indirectly (the `gauges_snow` check and the `e$station_number == maxan` check). The box, `blue_line_key` and `name` are not held at all. Fix: refuse unless `identical(x$site, site)` for both series files, and bundle `x$site[...]`, not `site[...]`. `departure_site.R` saves `site` unmodified from `site_get()`, so the comparison holds today; I could not confirm on the run's rds, since `data/departure/` is absent on this machine. The sibling read in `scripts/departure_site_snow.R:166-172`, which checks the site rds by release and md5 only, predates this branch and has the same gap.
