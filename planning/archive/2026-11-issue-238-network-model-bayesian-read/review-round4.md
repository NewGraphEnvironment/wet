## Findings

- **[severity: bug]** scripts/temperature_bayesian_alignment_check.R:167. `unit_rx` allows zero or one space between a number and its unit (`[\s\x{00A0}\x{202F}\x{2009}]?`). So `6  °C` (two spaces, or two no-break spaces), `6&nbsp;°C`, `6 &deg;C` and `6 ° C` are never extracted, and a file holding any of them passes (each probe exits 0, with the figure count unchanged at 35). The round-3 fix added the no-break and thin space glyphs but not a repeated space or the HTML entities a markdown author uses to keep a number with its unit. So the row "extractor vs numbers as written" is not closed. Suggested fix: use `[...]*` for the space, accept `&nbsp;`/`&#160;`/`&#8239;` and `&deg;`/`&#176;`, and allow a space between ° and C. Or simpler: flag any `°`, `℃`, `degC`, `%`, `percent` or `&deg;` that no extracted number covers.
  - **Rule:** code-check.md, "A proxy is not the property". The extractor's pattern stands in for "a number written with a unit".

- **[severity: bug]** scripts/temperature_bayesian_alignment_check.R:263. Code spans are paired within a line, but a stray backtick still pairs with the next real span's opening backtick on the same line. Probe: `and a stray ` before 6 °C and `code` here.` exits 0, because the masked span ` before 6 °C and ` hides the number. The round-3 probe only covered a stray backtick pairing across lines. So the row "code spans vs prose" is closed across lines but not within one. Suggested fix: fail any line (outside a fence) whose backtick count is odd before masking.
  - **Rule:** code-check.md, "A guard's scope, escape hatches, and remedies". An exemption (the masked span) grows to cover prose.

- **[severity: bug]** scripts/temperature_bayesian_alignment_check.R:267. `mark_rx` cannot count a closing single mark (U+2019, or `'` after a letter), because it looks like an apostrophe. Only the opening single mark counts, and only within `near` (200) characters of the page citation. So a single-quoted passage longer than about 160 characters escapes the scan. Probe: a `‘…’ (mcelreath2020StatisticalRethinking, p. 408)` passage of about 270 characters exits 0, while the same quote at 40 characters fails. Rows of this length already exist: the "Varying intercepts…" quote is about 170 characters. So the row "quote marks vs the near-citation scan" is closed for guillemets but not for single quotes. Suggested fix: also count a `’`, or a `'` after a letter, as a mark when it is followed by `sp_rx*` and `(` or `[@` and a citekey.
  - **Rule:** code-check.md, "A guard's scope, escape hatches, and remedies", its paragraph that a verbatim-quote check must hold every quote mark.

- **[severity: bug]** scripts/temperature_bayesian_alignment_check.R:399 with registry line 131. The whole-line anchor holds a value only when that value is written on the anchor's line. `registry` covers the remaining formals and constants by name only. Concretely, `start_date`/`end_date` are mapped to `gsdd_season`, whose anchor is R/wet_temp_gsdd.R:79 (the `gsdd::gsdd(` call). Their values live on the signature line, R/wet_temp_gsdd.R:54, which no anchor, figure or walk holds. Probe in a worktree: changing `as.Date("1972-03-01")` to `as.Date("1972-05-01")` leaves the review run at PASS (exit 0), while research/temperature_bayesian_alignment.md:79 still says the season runs "between March and November". `n_e2e <- 5`, `seed <- 213`, `z_max <- 3` (scripts/temp_baseline_recover.R:62-65) and `tb_digits <- 1` (scripts/temp_baseline_rule.R:13) are likewise covered by rows anchored on other lines, so their values move unchecked. So the row "anchor vs the line" is closed only for values on the anchor line, and "registry" holds names, not values. Suggested fix: for each registry entry, also require its own assignment or formal-default line, read whole, as a second anchor. Or give `start_date`/`end_date` an anchor on line 54.
  - **Rule:** code-check.md, "A proxy is not the property". The row's anchor stands in for the value the row describes (cf. code-check-r.md, "`deparse(body(f))` excludes formal defaults…": a default sits where a body scan does not look).

- **[severity: bug]** research/temperature_bayesian_alignment.md:3. The "Produced by" line says every figure is held to its source ("every choice held to its line and every figure to its source"). The check holds only numbers with a unit or a minus sign. Unsigned figures without a unit are not held: "1,600 times" (line 63), "at most 0.999" (line 39), "1 March to 30 November" (line 71), "7-day mean" (line 79), "persistence near 1" (line 65). Probes changing "1,600 times" to "16,000 times" and "at most 0.999" to "at most 0.99" both exit 0. These are digits, so they are not the accepted "numbers in words" residual. The enumeration row "a figure with no unit" is closed for signed numbers only. CLAUDE.md's wording ("every figure with a unit") is accurate; the research file's is not. Suggested fix: narrow the header to "every figure with a unit or a sign", or list and hold the unitless figures too.
  - **Rule:** writing.md, "Check that each guard covers the set its sentence names".

- **[severity: fragile]** scripts/temperature_bayesian_alignment_check.R:175. In `edge_rx`, the trailing guard `(?![0-9])` still accepts a decimal continuation: the literal `tb_displace <- 10` is found in `tb_displace <- 10.5   # …` (checked in R: TRUE). Likewise `tb_close <- 50` in `50.5`, or a thousands comma. Today the two integer-ending literals (`10 °C-days`, `50 °C-days`) are also anchored whole-line, so a review run still fails on them. But an `MD=` run (no anchors) and any future integer-ending literal rest on `edge_rx` alone. So the row "source literal vs its source: whole at numeric edges" is not closed for a point or comma followed by a digit. Suggested fix: `(?![0-9]|[.,][0-9])`, and the matching `(?<![0-9][.,])` on the leading side.
  - **Rule:** code-check.md, "A guard that fails toward pass".

## Enumeration, pair by pair

- extractor vs numbers as written: **not closed**. Repeated spaces, `&nbsp;`, `&deg;` and `° C` escape (finding 1). The listed probes (emphasis, ºC, ℃, percent, en-dash sign, `5–10`) fail as claimed.
- extractor vs matcher (one `dash` set): **closed**. The class `[\-‐-―−]` parses as a hyphen, U+2010–U+2015 and U+2212 in every regex that pastes it.
- a figure with no unit: **closed for signed numbers only**. Unsigned unitless figures are unchecked (finding 5).
- figure text vs a listed number elsewhere: closed as accepted (context words).
- source literal vs its source: **closed at a digit, not at a decimal continuation** (finding 6).
- anchor vs the line: **closed for values on the anchor line**. Formal defaults and constants written on other lines are not held (finding 4).
- registry vs values passed by position: **closed** for every current call shape (5 calls, all in scope scripts, `wet_fill_prepare` and `wet:::wet_fill_prepare`). A call through `do.call`/`Map`/an alias would not be seen.
- code spans vs prose: **closed across lines, not within a line** (finding 2). Per-line offsets are correct: a code span on a line with multibyte characters masks exactly.
- quote citation vs spacing (`sp_rx`): **closed**. An invented quote at `p.` + U+202F fails on the page.
- quote marks vs the near-citation scan: **closed for guillemets and short single quotes, not for a single-quoted passage longer than about 160 characters** (finding 3).
