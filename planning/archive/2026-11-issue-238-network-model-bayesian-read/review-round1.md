## Findings

- **[severity: bug]** scripts/temperature_bayesian_alignment_check.R:325 (and :323) — the figure guard compares by substring, not by number. An unlisted number with a unit passes whenever its text is a substring of any listed figure's text (`grepl(x, f, fixed = TRUE)`): "7 °C" is inside "128.7 °C-days", "1 °C" inside "about 11 °C-days" and "4.1 °C-days", "4 %" inside "89 to 94 %", "0 °C" inside "10 °C-days" and "298.0 °C-days", "5 %" inside "nominal 95 %", and so on. Reproduced: appending "The fill misses by 7 °C at one station, 1 °C at another, and 4 % of days are wrong." to a copy of the research file and running with `MD=` that copy still prints `figures: 24 numbers with a unit; ...` and `PASS`. The forward check at :323 has the same flaw the other way: a listed figure counts as "in the file" when its text sits inside a longer number ("0 °C" is found in "10 °C-days", "4 °C" in "130.4 °C-days"), so removing the standalone figure from the prose would not trip "listed but not in the file". The guard exists to hold every number with a unit to its source; as written it waves through any short number that happens to be a tail of a listed one. Compare whole tokens: extract `unit_rx` matches from each listed text and require `x %in%` that set, and test presence with a pattern that cannot start mid-number (a `(?<![0-9.])` lookbehind).
  - **Rule:** code-check.md "A guard that fails toward pass" ; code-check.md "A proxy is not the property"

- **[severity: fragile]** scripts/temperature_bayesian_alignment_check.R:165 — `unit_rx` allows only `\s?` between number and unit, and PCRE's `\s` (no UCP) does not match a no-break or narrow no-break space. A figure written "3 °C" or "298.0 °C-days" is never extracted, so it escapes the guard entirely. Reproduced: a copy with "misses by 3 °C" appended passes with the same 21-number count. The quote half handles exactly this (`sp_rx` names `\x{00A0}` because "PCRE's \s alone does not match" it); the figure half, new on this branch, does not. Neither research file holds a no-break space today, so nothing is wrong now; an editor or a paste that inserts one silently disables the check for that figure.
  - **Rule:** code-check.md "A guard that fails toward pass"

- **[severity: bug]** research/temperature_bayesian_alignment.md:31 and research/temperature_network_model.md:48 — "It removes flow-connected stations only, so stations on sister tributaries ... stay in training" / "The leak-free pool removes flow-connected stations only: stations on sister tributaries ... stay in". False against the code. The leak-free pool's training set is `tr = fold != fold[i] & !related[i, ]` (scripts/temp_baseline_lib.R:197): the held-out station's whole fold, its WSC sub-sub-drainage (`substr(station_number, 1, 4)`, R/wet_cv_folds.R:37, which temp_baseline_traits.R uses at its default), is removed as well as every flow-connected station. So sister tributaries inside the same sub-sub-drainage, which are the nearest ones and the ones a tail-down covariance would weight most, are out of training in both pools; only those in other sub-sub-drainages stay. network_model.md:48 contradicts itself within the bullet (it names "the same folds" and then says only flow-connected stations are removed). Both files are public and these sentences feed #223's design question (what a tail-down covariance could borrow on the holdout), so a reader would expect the holdout to leave in neighbours it in fact removes. The check script cannot catch this: it holds the row's line, not the sentence. State it by the code's definition: the leak-free pool removes the held-out station's sub-sub-drainage and every station upstream or downstream of it elsewhere; sister tributaries in other sub-sub-drainages stay.
  - **Rule:** none
