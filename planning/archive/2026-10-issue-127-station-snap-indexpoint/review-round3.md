## Mechanism

All three earlier findings come from one assumption: **the guard decides "this migration cannot end the trial's transaction" by re-implementing PostgreSQL's lexer and grammar as a regex deny-list over the file's text, and it reads "no match" as "safe".** Any difference between the regex's model and the server's model fails toward pass. That covers the separators between words (round 1), the terminators (round 1) and the regex engine giving up (round 2). The check that tests the real property, that the session still holds the same transaction, runs only after the write. The text match stands in for "nothing this run does persists", so it misses three more kinds of path:

1. **Spellings of transaction statements.** The author's list of statements is complete for PostgreSQL 17's grammar. `TransactionStmt` has ABORT, COMMIT and ROLLBACK, each with opt_transaction and opt_transaction_chain; START TRANSACTION; SAVEPOINT, RELEASE and ROLLBACK TO; PREPARE TRANSACTION; and COMMIT or ROLLBACK PREPARED. `TransactionStmtLegacy` adds BEGIN and END. Of these, only ABORT, COMMIT, END, ROLLBACK and PREPARE TRANSACTION end the block. COMMIT and ROLLBACK PREPARED, and COMMIT inside DO or CALL in an explicit block, raise an error instead (measured: "invalid transaction termination"). The anchoring claim also holds. In the simple query protocol a statement starts only at the start of input or after a `;` the server lexes. From that real `;`, only real whitespace and comments come before the keyword. The regex's comment grammar matches the server's: nesting, `/*/`, `**/`, and `--` inside `/* */` and the reverse. PCRE's `\s` covers more than the server's `[ \t\n\r\f\v]`. The one divergence I found is that the server ends a `--` comment at `\r` and the regex does not. `"SELECT 1; -- c\rCOMMIT;"` passes `wet_pg_trial_sql()`, but `wet_pg_trial()` reads the file with `readLines()`, which treats a lone CR as a line end (measured: it reaches the scan as `\n` and is refused). So that case is reachable only by calling the internal function directly. Invalid UTF-8 in the file makes `strsplit()` return `NA`, so the body becomes the string `"NA"` and the server gets a syntax error. That fails closed, by accident. A NUL truncates the line in what is scanned and in what runs alike. NBSP after a keyword lexes as part of an identifier, which is a syntax error. Because the server parses the whole simple-query string before it runs any of it, every lexer or parser error means nothing runs.
2. **Commits that are not transaction statements.** No text pattern for transaction statements can see these, and the xid check cannot either, because the session's own transaction is untouched. See the finding below.
3. **The R client inside the trial.** RPostgres's `dbWriteTable()` sends its own `BEGIN`/`COMMIT` whenever its client-side flag says no transaction is open. `wet_pg_trial()` opens the transaction with `DBI::dbBegin()`, which sets that flag, so `wet_station_snap()`'s temp tables use the `SAVEPOINT "dbWriteTable"` path (read from RPostgres 1.4.10's methods). This is safe as written. Nothing re-checks the xid after the code that runs inside the trial, though. In the sweep, the args check on the third connection is the only after-the-fact check. The tests have none. Anyone opening the trial with `dbExecute(conn, "BEGIN")` would turn every `dbWriteTable()` into a commit.

Other places the mechanism reaches, checked and clean:

- `check_aborted()` matches English server text, and `lc_messages` is `en_US.utf8` here. Any escaped error also makes the next `SAVEPOINT` in `try_sql()` raise outside its `tryCatch()`, so the run stops either way.
- The `own` line regex can only refuse wrongly.
- The report's `grep_hits` line is report text only.

## Findings

- **[fragile]** `R/wet_pg_trial.R:7-11, 12-24` and `CLAUDE.md:88` ("tried, never applied"): a migration can commit to the shared database without using a transaction statement, and neither guard sees it. On this server (PostgreSQL 17.5, measured with `pg_extension`):
  - **`dblink` is installed.** `SELECT dblink_exec('dbname=fwapg', '…')` runs on a second connection in autocommit, so it is committed at once. The trial's transaction and xid are untouched, so the xid check passes.
  - **The trial connects as superuser `postgres`.** Server-side `COPY … FROM/TO PROGRAM '…'` therefore runs any shell command on the database host, and a `psql -c` there commits in its own session.
  - **`setval()` is not transactional.** A migration that resets a sequence leaves the shared database's sequence moved after the rollback. If it moves the sequence backwards, later inserts collide with existing keys. `nextval()` consumed by inserts into serial columns also persists, but only as gaps.

  Not available here: `pg_background`, `plpython3u` and `plperlu`. `postgres_fdw` is available but not installed, and it aborts its remote transaction when the local one rolls back, so it is not a path.

  This is not reachable with today's input. fwapg b088b43's `db/migrations/` has no `dblink`, `setval`, `nextval` or `PROGRAM`. The `\copy … FROM PROGRAM` lines are in `load/`, and they are psql meta-commands, which the server rejects with a syntax error. The claim in the docs is still wider than the guard, and the guard's one contract is to never migrate the shared database.

  Fix: refuse the words `dblink`, `PROGRAM`, `setval` and `pg_background` anywhere in the body, case-insensitively at word boundaries; false refusals are accepted. Or narrow the sentence in `CLAUDE.md` and the file header to "refuses transaction control; does not stop a migration that writes through another connection". The two fixes are not alternatives for safety: only the first closes the path.

  A mechanism-level option for the statement half, if wanted: run the body as `DO $<tag>$ BEGIN EXECUTE $<tag2>$<body>$<tag2>$; END $<tag>$`, with each tag checked absent from the body. Measured on this server in rolled-back transactions that touched nothing: a multi-statement `EXECUTE 'SELECT 1; SELECT 2'` runs; `EXECUTE 'SELECT 1; COMMIT'` and `EXECUTE 'END'` raise "EXECUTE of transaction commands is not implemented"; a nested `DO $$ BEGIN COMMIT; END $$` raises "invalid transaction termination". The server then refuses every spelling of a transaction statement, with no lexer in R. It does not close the dblink, PROGRAM or setval paths, and server error positions would point inside the `EXECUTE`.

- **[fragile]** `scripts/station_snap_sweep.R:253, 342, 353, 360`: the migration's provenance is read from the path when the report is written, not from what ran. `wet_pg_trial()` reads the file once, at line 234. After the run, which takes minutes, the md5 in the rds and the report is computed again, and the "Issue's check … on the body the trial ran" line re-reads and re-strips the file. If the file is rewritten during the run, the report attributes the counts to a migration that was not applied. One example is another `git show <commit>:… > <file>` for a different commit. `WET_FWAPG_MIGRATION_COMMIT` is captured at start, so the commit and the md5 can then disagree with no tell. Fix: read the file and take its md5 once, before the first connection. Pass that text to the trial, for example by letting `wet_pg_trial()` accept the body or by writing a frozen temp copy. Use the same text for the grep line. The tracked report is unaffected: the file did not change during that run.
