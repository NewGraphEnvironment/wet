## Findings

- **[fragile]** `R/wet_pg_trial.R:43-49` (`wet_pg_trial_sql()`): the pre-run refusal misses transaction control whose words are split by a line break or a comment, and a final statement with no semicolon. The separator inside the multi-word forms is `s <- "[ \\t]+"` and the pattern must end in `;`, so these pass straight through (probed by sourcing the file, no database):
  - `"SELECT 1;\nCOMMIT\nAND CHAIN;"` -> passed through
  - `"SELECT 1;\nEND\nTRANSACTION;"` -> passed through
  - `"SELECT 1;\nROLLBACK /* x */ WORK;"` -> passed through
  - `"SELECT 1;\nCOMMIT -- c\nWORK;"` -> passed through
  - `"SELECT 1;\nCOMMIT"` (last statement, unterminated) -> passed through
  - control: `"SELECT 1;\nCOMMIT AND CHAIN;"` -> refused

  The server accepts all of these, and a simple-query string runs an unterminated last statement. Each ends the trial's transaction inside `dbExecute(..., immediate = TRUE)`, so everything before it is **committed to the shared database**; the xid check after the call then stops with "may have been committed", i.e. it detects the migration after it has been applied rather than preventing it (the "check that exists only in the post-write verifier" shape). The comment ("Whitespace, line breaks and comments may sit around the keyword, as the server allows") reads as covering this, but only the space around the keyword, not between its words, is handled. Fix: use the comment-and-whitespace class `ws` (one or more) as the separator inside `opt` and inside `START TRANSACTION` / `PREPARE TRANSACTION`, and accept end of input as a terminator (`(;|\\z)` with `\\z`, not `$`, which under `(?m)` would match plpgsql's bare `BEGIN` lines). Add the five cases above to the `refuse()` list. Low likelihood with fwapg's current migrations (one `BEGIN;` / `COMMIT;` pair), but this function's one contract is never migrating the shared database.

- **[fragile]** `scripts/station_snap_sweep.R:154-178` (`try_sql_snap()`), via `R/wet_station_snap.R:44-45` and `:85-86`: the per-call savepoint promise ("a call that errors or hangs is counted and the sweep goes on") does not hold for `wet_station_snap()`. It creates a temp table and registers `on.exit(DBI::dbRemoveTable(...))`. When any of its later queries errors (including the `statement_timeout` the script sets exactly to catch hangs), the transaction is aborted, so the `on.exit` `DROP TABLE` itself fails with "current transaction is aborted…", and R hands that second error to `tryCatch()` in place of the first (measured: `f <- function() { on.exit(stop("cleanup")); stop("orig") }; tryCatch(f(), error = function(e) conditionMessage(e))` returns `"cleanup"`). Both the all-stations call and the one-at-a-time fallback then record "current transaction is aborted" as the station's error, and `check_aborted()` stops the run with "the run's transaction was aborted", blaming an error that escaped a savepoint when none did and losing the real cause. It fails loud, and the committed run never hit it (490 picks on both sides, 0 snap errors), but a real snap error or timeout under a future migration would kill the sweep with a wrong diagnosis instead of being counted. Fix in the script: capture the original condition with `withCallingHandlers()` (record the first error's message in a variable before unwinding) and report that, or roll back to the savepoint before cleanup can run (e.g. call `wet_station_snap()` inside a wrapper that does `ROLLBACK TO SAVEPOINT` in a calling handler). The same masking applies to `wet_snap_lake()`'s temp table.
